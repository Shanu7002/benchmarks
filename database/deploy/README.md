# Deploying dbbench to AWS

Infrastructure templates for running `dbbench` against **real** databases instead of
Docker on a laptop. There are two equivalent implementations, pick one:

- `terraform/`: Terraform
- `cloudformation/`: CloudFormation (single template)

> **Status: written and statically validated, never applied.** See
> [What has and hasn't been verified](#what-has-and-hasnt-been-verified). Read it before the
> first `apply`, and expect to fix small things on first contact with a real account.

## 1. What you get

```
                       your laptop
                            │  aws ssm start-session  (no SSH, no open ports)
                            ▼
   ┌───────────────────────── VPC 10.42.0.0/16 ─────────────────────────┐
   │  public subnet (AZ a)              private subnets (AZ a, AZ b)    │
   │  ┌──────────────────┐              ┌─────────────────────────────┐ │
   │  │ runner EC2       │──5432───────▶│ RDS PostgreSQL (AZ a)       │ │
   │  │ (t4g.small)      │──3306───────▶│ RDS MySQL      (AZ a)       │ │
   │  │ dbbench-run      │              │ no internet route           │ │
   │  └───────┬──────────┘              └─────────────────────────────┘ │
   └──────────┼─────────────────────────────────────────────────────────┘
              │ HTTPS (S3, Secrets Manager, SSM)
              ▼
     S3 artifacts bucket: dbbench binary, dbbench-run.sh, optional targets.yml, results/
```

| Piece | Why |
|---|---|
| **Runner EC2 in the same AZ as the DBs** | Network latency is part of every measurement. Same region *and* AZ keeps it small and equal for all engines |
| **DBs in private subnets, not publicly accessible** | Nobody can reach them from the internet; only the runner's security group can connect |
| **Runner has no inbound rules** | You get a shell through SSM Session Manager, so there is no SSH key and no port 22 |
| **Passwords generated by RDS into Secrets Manager** | No password in variables, state, templates or git. The runner reads it at run time |
| **No NAT gateway** | It bills by the hour. The runner is in a public subnet with a public IP but zero inbound access; DBs never need the internet |
| **S3 bucket** | Moves the binary and script in, and the results out, without SSH/scp |
| **Same instance class and storage for every DB** | Otherwise results aren't comparable |

## 2. Cost and safety guardrails (in the infrastructure)

These mirror the guardrails in the Go code (see `GETTING_STARTED.md`, section 4).

| Guardrail | Terraform | CloudFormation |
|---|---|---|
| Small DB size by default (`db.t4g.micro`) | `db_instance_class` | `DbInstanceClass` |
| Storage capped at 20-100 GB, **autoscaling off** (a runaway test hits a wall) | `db_storage_gb` (validated 20-100) | `DbStorageGb` (Min 20 / Max 100) |
| No Multi-AZ, no backups, no deletion protection, no Performance Insights | in `aws_db_instance` | in `AWS::RDS::DBInstance` |
| Runner **stops itself** after a TTL (default 4h) | `runner_ttl_minutes` | `RunnerTtlMinutes` |
| Optional monthly **budget alert** on resources tagged `Project=dbbench` | `budget_email`, `budget_usd` | `BudgetEmail`, `BudgetUsd` |
| Every resource tagged `Project=dbbench` | provider `default_tags` | `Tags` on each resource |
| IMDSv2 only, encrypted volumes and storage, bucket blocks public access | yes | yes |
| Runner IAM limited to its bucket and the DB secrets | exact ARNs | exact ARNs |
| Runner egress limited to 443 and the DB ports | security group rules | security group |

### Configurable values (nothing hard-coded)

Everything below is a Terraform variable and a CloudFormation parameter, with validation:

| Setting | Terraform | CloudFormation | Default |
|---|---|---|---|
| Region | `region` | stack region | `us-east-1` |
| Initial database name | `db_name` | `DbName` | `bench` |
| Master username | `db_username` | `DbUsername` | `dbbench_admin` |
| PostgreSQL / MySQL port | `postgres_port` / `mysql_port` | `PostgresPort` / `MysqlPort` | `5432` / `3306` |
| Runner AMI | `runner_ami_ssm_parameter` | `LatestAmiId` | AL2023 arm64 |
| VPC CIDR | `vpc_cidr` | `VpcCidr` | `10.42.0.0/16` |

The database name and ports are passed to the runner through `/etc/dbbench/env`, so the
connection strings the script builds always match what was deployed. The Go-side safety limits
and defaults are configured separately in `config/` (see `GETTING_STARTED.md`, section 3.6).

Two things the stack **cannot** do for you:

- **The TTL only stops the runner.** The RDS instances keep billing until you destroy the
  stack. Always tear down (section 7) and verify nothing is left.
- **The budget needs the cost allocation tag `Project` activated** in *Billing → Cost
  allocation tags*, which can take up to 24 hours to take effect. Until then it alerts on nothing.

## 3. Prerequisites

- An AWS account you're allowed to create VPCs, RDS, EC2, IAM roles and S3 buckets in. **Use a sandbox/dev account, not production.**
- AWS CLI v2 configured (`aws sts get-caller-identity` works), plus the
  [Session Manager plugin](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html).
- Go (to build the binary), and either Terraform >= 1.5 or nothing extra for CloudFormation.

## 4. Build the binary

The runner is arm64 (Graviton, cheaper). Build a static Linux arm64 binary:

```bash
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o dist/dbbench ./cmd/dbbench
```

(`dist/` is git-ignored. Want x86 instead? Build with `GOARCH=amd64`, pick a non-`g` instance type such as `t3.small`, and use the x86 AMI path in the template.)

## 5. Create the infrastructure

### Option A: Terraform

```bash
cd deploy/terraform
cp terraform.tfvars.example terraform.tfvars      # git-ignored; edit region, tags, budget
terraform init
terraform plan -out tfplan                         # READ the plan: a few dozen resources (VPC, subnets, security groups, S3, IAM, 1-2 RDS, 1 EC2)
terraform apply tfplan
```

Useful outputs afterwards: `terraform output artifacts_bucket`, `terraform output -raw ssm_session_command`.

### Option B: CloudFormation

```bash
aws cloudformation deploy \
  --region us-east-1 \
  --stack-name dbbench \
  --template-file deploy/cloudformation/dbbench.yaml \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides DbStorageGb=20 EnableMysql=true EnablePostgres=true

aws cloudformation describe-stacks --stack-name dbbench --region us-east-1 \
  --query 'Stacks[0].Outputs' --output table
```

Creating the RDS instances takes several minutes.

## 6. Run a benchmark

**a. Upload the binary and run script** (bucket name comes from the output above):

```bash
BUCKET=<artifacts bucket output>
aws s3 cp dist/dbbench                       s3://$BUCKET/dbbench
aws s3 cp deploy/scripts/dbbench-run.sh      s3://$BUCKET/dbbench-run.sh
# optional: your own targets/params (otherwise a sensible default is generated)
aws s3 cp targets.yml                        s3://$BUCKET/targets.yml
# optional: override the embedded config/defaults.yml and/or limits.yml (no rebuild needed;
# a missing file falls back to the embedded one, and the plan output prints the source)
aws s3 cp config/limits.yml                  s3://$BUCKET/settings/limits.yml
```

**b. Open a shell on the runner** (no SSH):

```bash
aws ssm start-session --region us-east-1 --target <runner instance id>
```

**c. Run.** The `dbbench-run` wrapper downloads the latest binary and script, reads the
DB passwords from Secrets Manager, builds the DSNs, runs, and syncs results to S3:

```bash
dbbench-run list                                  # scenarios and dialects
dbbench-run pg-rds    bulk_insert  -dry-run        # ALWAYS preview first
dbbench-run pg-rds    bulk_insert
dbbench-run mysql-rds bulk_insert
dbbench-run pg-rds    point_lookup
dbbench-run mysql-rds point_lookup
```

The targets are named `pg-rds` and `mysql-rds`. The label saved with every result
includes engine version, instance class, storage and region, so results from different
environments stay distinguishable.

The Go guardrails still apply: RDS hostnames count as **remote** targets, so the remote
limits apply (up to 50M rows, 20 GiB estimated). Raise them deliberately, never with `-force` by habit.

**d. Fetch results to your laptop:**

```bash
aws s3 sync s3://$BUCKET/results ./results
```

## 7. Tear down (do not skip)

```bash
# Terraform
cd deploy/terraform && terraform destroy

# CloudFormation: the bucket must be empty first
aws s3 rm s3://$BUCKET --recursive
aws cloudformation delete-stack --stack-name dbbench --region us-east-1
aws cloudformation wait stack-delete-complete --stack-name dbbench --region us-east-1
```

Then verify nothing is still billing:

```bash
aws rds describe-db-instances --region us-east-1 \
  --query 'DBInstances[?starts_with(DBInstanceIdentifier, `dbbench`)].DBInstanceIdentifier'
aws ec2 describe-instances --region us-east-1 --filters Name=tag:Project,Values=dbbench \
  --query 'Reservations[].Instances[?State.Name!=`terminated`].InstanceId'
```

Both must print `[]`. Download your results (section 6d) **before** destroying.

## 8. Implementing it properly

Follow this order. Don't skip to a big instance first.

**Before the first apply**
1. Use a **dedicated sandbox account** (or at least a dedicated region) so a mistake can't touch real workloads, and so the budget/tag filter is meaningful.
2. Activate the `Project` **cost allocation tag** and set `budget_email`.
3. **Review the plan.** Terraform: `terraform plan`. CloudFormation: use a change set (`aws cloudformation deploy --no-execute-changeset`). Confirm nothing is public.
4. **Pin engine versions** (`postgres_version = "16.x"`) once you have a first result. A major-only version resolves to the newest minor at apply time, so the same code can produce different environments months apart.

**Making results meaningful**
5. `db.t4g.micro` and `t4g.small` are **burstable**: CPU credits run out under sustained load and results drift. They are fine for proving the pipeline. For real comparisons use non-burstable classes (for example `db.m7g.large` and `m7g.large`) and **keep every database on the same class**.
6. Run each scenario **several times** (3+) and compare medians, not a single run. The first run warms caches.
7. Keep the runner and DBs in the **same AZ** (already the default). Never run the runner from your laptop against RDS; the internet dominates the numbers.
8. Always check `errors` in the output. Anything above 0 invalidates the run.
9. One change at a time: instance class, storage size, engine version, or scenario params. Otherwise you can't attribute the difference.

**Operating it**
10. **State:** the Terraform here uses local state, fine for one person and a disposable stack. If several people share it, move to a remote backend (S3 bucket with versioning plus DynamoDB or S3 native locking) before anyone else runs `apply`.
11. **Keep both IaC versions in sync.** They are intentional mirrors. Any change to networking, security groups, IAM, instance settings or parameters goes in **both**, in the same PR. The shared logic lives in `scripts/dbbench-run.sh` precisely so it isn't duplicated.
12. **CI checks** (cheap, no AWS needed): `terraform fmt -check -recursive`, `terraform init -backend=false && terraform validate`, `cfn-lint deploy/cloudformation/dbbench.yaml`, and `shellcheck deploy/scripts/dbbench-run.sh`.
13. Commit `terraform/.terraform.lock.hcl` so provider versions are reproducible. Never commit `terraform.tfvars`, state files, or results (all git-ignored).

## 9. Adding another database engine

Say you add `mariadb` or `sqlserver` to dbbench (see `CONTRIBUTING.md`). Then, in **both** IaC versions:

1. Add an `enable_<db>` variable/parameter and an `aws_db_instance` / `AWS::RDS::DBInstance` mirroring the existing ones (same class, storage, subnet group, security group).
2. Add the engine's port to the DB security group ingress and the runner's egress.
3. Add its secret ARN to the runner IAM policy, and its `*_HOST`, `*_SECRET_ARN`, `*_LABEL` to the user-data env file.
4. In `scripts/dbbench-run.sh`: add the target to the generated `targets.yml` and build its DSN from the secret (mind URL-encoding rules for that driver).
5. Run the checks in section 8, step 12, and update the diagram and tables in this file.

## 10. Troubleshooting

| Symptom | Likely cause |
|---|---|
| `aws ssm start-session` can't find the instance | Instance not yet registered (wait 2-3 min after boot), no outbound 443, or the Session Manager plugin isn't installed locally |
| `dbbench-run: command not found` | user-data hasn't finished or failed: `sudo cat /var/log/cloud-init-output.log` |
| `aws s3 cp ... NoSuchKey` | Binary / script not uploaded yet (section 6a) |
| `exec format error` | Binary built for the wrong architecture. Rebuild with `GOARCH=arm64` for `t4g` |
| `ping: ... timeout` connecting to the DB | RDS still creating, or you changed the security groups/AZs |
| `refusing to run (remote target limits)` | The Go guardrail; lower the params in `targets.yml` |
| Runner disappeared mid-run | The TTL stopped it. Raise `runner_ttl_minutes`; start it again with `aws ec2 start-instances` |
| `terraform destroy` fails on the bucket or DB | Re-run it; if a DB is stuck, check `aws rds describe-db-instances` |
| CloudFormation delete fails on the bucket | It wasn't emptied first (section 7) |

## 11. What has and hasn't been verified

**Verified on a laptop, without touching AWS:**

- `terraform fmt -check`, `terraform init -backend=false` and `terraform validate` pass.
- The user-data template renders correctly with sample values (escaping of `$` verified).
- `cfn-lint` reports no findings on the CloudFormation template.
- `scripts/dbbench-run.sh` ran end to end with a stubbed `aws` CLI: it generated `targets.yml`, built both DSNs from a secret with a deliberately nasty password (`p:a?s#s%w&rd!`), and the real Postgres URL parser and MySQL DSN parser decoded it back to the original. RDS hostnames are classified as *remote* by the guard.
- The static `linux/arm64` binary cross-compiles.

**Not verified (no AWS credentials were available):**

- `terraform plan` / `apply` and `aws cloudformation deploy` have never been run. Real-account issues such as quotas, service-linked roles, an unavailable engine version in your region, or IAM permission boundaries would only show up there.
- The runner booting, SSM registration, the S3/Secrets Manager calls, and connecting to RDS are untested.
- The two stacks have not been compared against each other by deploying both.
- `aws ssm send-command` (non-interactive runs) is untested. The wrapper uses `$HOME`, which may be unset there; if you automate it, set `DBBENCH_DIR=/opt/dbbench` for the command.
- Cost figures are deliberately not stated here. Use the AWS Pricing Calculator for your region and keep the budget alert on.

Do the first deployment in a sandbox account, with the defaults, and run `-dry-run` before anything else.
